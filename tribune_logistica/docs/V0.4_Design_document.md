## 1. Overview

Book Legion is a web-based EPUB reader with two parallel content consumers:

- **Text consumer** — renders chapter HTML in a browser viewport, paginated or scrolling
- **TTS consumer** — strips HTML, synthesises audio, and streams quantized chunks to the client

Both consumers share a single position model and can be synchronised bidirectionally. The server is the authority on reading position, and both clients report into the same coordinate space.

## 3. Position Model

### 3.1 Canonical Position

All positions within a chapter are expressed as a **zero-based HTML character offset** into the raw chapter HTML string as served by the backend.

```
{ chapterIndex: number, htmlCharOffset: number }
```

This is the single coordinate space shared by all consumers and the server. Neither consumer invents its own position representation; both project onto this space.

### 3.2 Why HTML Offset

- The text consumer natively operates in HTML offset space — it can directly observe the offset of the first rendered character
- The backend slices chapter HTML at known offsets before stripping for TTS, so `htmlStartOffset` and `htmlEndOffset` of every chunk are known prior to stripping
- Restoring a saved cursor is a direct scroll-to-offset with no fuzzy search
- Positions are meaningful outside the client: they can be stored server-side, synced across sessions, and used for progress calculation without client-specific decoding

### 3.3 Chapter Boundary Sentinel

`∞` (represented as `-1` or `null` in JSON) is used as a sentinel value in offset fields to indicate a chapter boundary. See [Section 7](#7-navigation-protocol) for the full protocol.

## 4. Chunk Boundary Authority

### 4.1 Core Principle

The backend is the sole authority on where valid chunk boundaries fall. Neither consumer is permitted to independently decide that a split occurs at an arbitrary offset.

This prevents drift: if both consumers ask for the nearest valid split to a given offset, they are guaranteed to receive the same canonical offset back. Chunk transitions in both consumers are structurally aligned.

### 4.2 The Split Function

```
nearestAllowedSplit(html, current, target) → canonicalOffset
```

**Valid split positions** are offsets that satisfy all of the following:
- Falls between HTML tags, never inside one
- Falls at a word boundary (whitespace, punctuation) in the stripped text
- Produces a non-empty chunk in both directions from the split
- Falls within `[current, target]`
- Always find the closest boudnary to target, which is in between current and target
- Current can be larger than target, when going backwards


### 4.3 How Each Consumer Uses It

**Text consumer** — calculates a desired split from viewport geometry (where a page break wants to fall) and submits that to `nearestAllowedSplit`. The returned offset is used to determine chunk membership for cursor reporting.

**TTS pipeline** — calculates a desired split from a target duration (approximately 30 seconds of speech) using word-count estimation, then submits to `nearestAllowedSplit`. The returned offset becomes the `htmlStartOffset` of the next clip.

### 4.4 Chunk Offset Map

When a chapter is loaded, the backend computes and returns the HTML char offset of every chunk boundary in that chapter:

```json
{
  "chapter_index": 2,
  "num_chunks": 5,
  "chunk_offsets": [0, 1842, 3701, 5534, 7200],
  "text": "..."
}
```

The text consumer uses this map to determine which chunk contains the current viewport position without a round-trip.

## 5. Consumer Synchronisation

### 5.1 Position Reporting

Both consumers report position to the server as `{ chapterIndex, htmlCharOffset }`. The server stores this as the user's cursor for the book.

| Consumer | Precision | Reports on |
|---|---|---|
| Text | Exact | Page turn |
| TTS | Quantized — chunk boundary only | Each clip change |

### 5.2 Receiving a Sync Update

When the server pushes a position update originating from the other consumer:

**Text consumer receives `htmlCharOffset`:**
Binary-search `chunk_offsets` for the nearest boundary ≤ the offset, then scroll to that position.

**TTS consumer receives `htmlCharOffset`:**
Find the clip where `htmlStartOffset ≤ charOffset < htmlEndOffset`. Seek to the start of that clip. Maximum backward snap is one chunk length.

### 5.3 TTS Dead Zone

Between TTS clip events, the server has no updated position from the audio side. If the text consumer is following TTS, it receives an anchor at clip start and then nothing for up to ~30 seconds.

**Current behaviour (v0.4):** Text consumer holds at the clip's `htmlStartOffset` until the next clip event.

**Planned (v0.5):** Server dead-reckons from clip start using estimated speaking rate and pushes interpolated positions to the text consumer. The next real clip event corrects any drift.

## 6. TTS Pipeline

### 6.1 Per-Clip Workflow

For each chunk:

1. Backend selects chunk boundaries using `nearestAllowedSplit`, recording `htmlStartOffset` and `htmlEndOffset`
2. HTML between those offsets is extracted
3. HTML tags are stripped — one-way, backend only
4. Stripped plain text is sent to TTS synthesis
5. Audio clip and metadata are returned to client

### 6.2 Clip Metadata

Each audio clip carries:

```json
{
  "clipId": "ch3-clip-012",
  "chapterIndex": 3,
  "htmlStartOffset": 4821,
  "htmlEndOffset": 5203,
  "duration": 24.3
}
```

The client never needs to know the plain text. `htmlStartOffset` is the position it reports to the server when this clip begins playing.

### 6.3 Quantized Position

The TTS consumer can only report position at clip granularity. It reports `htmlStartOffset` when a clip starts, and is otherwise silent. It does not interpolate mid-clip.

This means the worst-case sync error between consumers is one chunk length in content terms — at typical speaking rates and 30s chunk targets, approximately one to two paragraphs.

## 7. Navigation Protocol For audio

All chunk requests carry `{ start, end }` offset fields. The sentinel value `null` means "chapter boundary / unknown."

### 7.1 Request Forms

| `start` | `end` | Meaning |
|---|---|---|
| `X` | `null` | Chunk starting at X, going forward |
| `0` | `null` | Start from beginning of chapter |
| `null` | `null` | Last chunk of chapter (no anchor) |
| `null` | `Y` | Chunk ending at Y (step backward from known position) |

### 7.2 Response Sentinel

When the backend returns `end: null`, that is the signal that this chunk reaches the natural end of the chapter. The client should request the next chapter on the next forward step.

```json
{
  "clipId": "ch3-clip-019",
  "chapterIndex": 3,
  "htmlStartOffset": 7200,
  "htmlEndOffset": null,
  "duration": 18.6
}
```

### 7.3 Chapter Transition Flows

**End of chapter, going forward:**
```
client receives clip with htmlEndOffset: null
→ plays clip to end
→ requests next chapter: { chapterIndex: N+1, start: 0, end: null }
```

**Start of chapter, going backward to previous:**
```
client is at start of chapter N, user navigates back
→ requests: { chapterIndex: N-1, start: null, end: null }
→ backend returns last chunk of chapter N-1
```

**Stepping backward from a known position:**
```
client knows htmlCharOffset Y
→ requests: { chapterIndex: N, start: null, end: Y }
→ backend returns chunk whose snapped end ≤ Y
```

## 9. Known Issues in v0.4

### 9.1 Clip Metadata Missing HTML Offsets

**Location:** `POST /api/v1/books/{book_id}/chunks` response

**Issue:** Audio clip responses do not include `htmlStartOffset` or `htmlEndOffset`. The TTS consumer therefore cannot report position in the canonical HTML offset space, and cannot participate in cross-consumer sync.

**Impact:** High — sync between text and audio is not possible in the current protocol.

---

### 9.2 Missing Chunk Offset Map

**Location:** `GET /api/v1/books/{book_id}/chapters/{chapter_index}` response

**Issue:** The chapter response returns `num_chunks` but not the actual HTML char offset of each boundary. The text consumer cannot determine which chunk it is inside without a round-trip, and cannot map its scroll position to a chunk without client-side recalculation.

**Impact:** Medium — progress reporting and sync anchoring are imprecise.

---

### 9.3 Snippet-Based Cursor Endpoint

**Location:** `POST /api/v1/books/{book_id}/chapters/{chapter_index}/cursor`

**Issue:** Accepts an `snippet_html` string and fuzzy-searches for it in the chapter to return a cursor. This is fragile: repeated phrases within a chapter produce ambiguous matches, minor whitespace differences between stored snippet and current HTML cause lookup failures, and content updates between app versions can silently corrupt saved positions.

**Impact:** Medium for v0.4, high if position persistence is relied on across app updates.

---

### 9.4 No `nearestAllowedSplit` Endpoint

**Issue:** There is no endpoint exposing the backend's split validation function to clients. Clients cannot ask the backend to snap an arbitrary offset to the nearest valid chunk boundary. As a result, the text consumer has no way to participate in canonical split resolution.

**Impact:** Medium — required before cross-consumer sync can be made drift-free.

---

## 10. v0.5 Roadmap

### 10.1 Add HTML Offsets to Clip Metadata

Extend the chunk response to include `htmlStartOffset` and `htmlEndOffset` on every clip. This is the minimum change required to unblock cross-consumer synchronisation.

```json
{
  "data": "...",
  "Cursor": { "Chapter": 1, "Chunk": 2 },
  "htmlStartOffset": 1842,
  "htmlEndOffset": 3701,
}
```

---

### 10.2 Expose `nearestAllowedSplit`

Add an endpoint the text consumer can call to validate a prospective split offset:

```
POST /api/v1/books/{book_id}/chapters/{chapter_index}/split
```

```json
// Request
{ "requestedOffset": 1900, "min": 1800, "max": 2000 }

// Response
{ "canonicalOffset": 1842 }
```


---

### 10.3 Replace Snippet Cursor with Offset Cursor

Remove `POST /api/v1/books/{book_id}/chapters/{chapter_index}/cursor` (snippet-based).

Replace with offset-based cursor save/restore:

```json
// Cursor shape going forward
{
  "UserID": "u1",
  "BookID": "b1",
  "Cursor": {
    "Chapter": 1,
    "htmlCharOffset": 1842
  }
}
```

The `Chunk` field can be derived from `htmlCharOffset` + `chunk_offsets` and does not need to be stored separately.

---

### 10.4 Navigation Protocol

Implement the `{ start, end }` sentinel-based navigation described in [Section 7](#7-navigation-protocol), replacing the current `requestSize` forward-only paging model. This enables backward navigation and end-of-chapter detection for the TTS consumer.

---

### 10.5 Server Dead-Reckoning for TTS Sync

When the TTS consumer is the position authority, the server interpolates position between clip events at an estimated speaking rate and pushes updates to the text consumer. The next real clip event corrects accumulated drift.

This removes the current behaviour where the text consumer stalls for up to 30 seconds waiting for the next TTS clip boundary.
